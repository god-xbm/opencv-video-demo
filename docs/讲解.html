一、你的电脑差点做不了这道题

开始动手之前，我先把这台电脑的「兵器库」翻了一遍，结果是这样的：

需要的东西当时的状况
CMake❌ 任何位置都没有
OpenCV❌ 库、头文件、配置文件，全都没有
Visual Studio / MSVC❌ 完全没装
C++ 编译器⚠️ 只有一个：Dev-C++ 自带的 TDM-GCC 4.9.2
vcpkg / conan / choco / scoop❌ 四个包管理器一个都没有

关键在那唯一一个编译器：它是 2014 年发布的。

为什么 TDM-GCC 4.9.2 干不了这件事？

  • 它的标准库目录里没有 <filesystem>。而这个作业要用 std::filesystem::create_directories 来「自动创建 output 目录」。
  • 它对 C++17 的支持是残缺的，而 OpenCV 5.x 的构建配置明确要求 cxx_std_17。
  • 它不支持 CMake 工程（Dev-C++ 5.11 只有自己的工程文件格式）， 而作业第一条就是「使用 CMakeLists.txt 管理工程」。

那为什么不直接下 OpenCV 官方的 Windows 安装包？因为那个包是 MSVC 编译的， 里面的 C++ 符号是 MSVC 的 ABI，MinGW 的链接器根本认不出来。想用它就得连 Visual Studio 一起装（3 GB 起步）。

最后的解法：MSYS2

它用 pacman 一条命令就能装齐「现代 GCC + CMake + Ninja + 预编译好的 OpenCV」， 而且这些包彼此出自同一套工具链，不存在 ABI 打架的问题。 相当于别人已经帮你把 OpenCV 编译好、还顺手配好了 CMake 配置文件。

过程中踩到的第一个真坑

照理说装完就完事了，但这里有个非常隐蔽的陷阱。

MSYS2 的 OpenCV 在编译时启用了 -DWITH_QT=ON——意思是窗口后端用的是 Qt， 不是 Windows 原生窗口。而 Qt 相关的两个包在 OpenCV 包里只被标成 optdepends（可选依赖），所以 pacman 不会自动帮你装。

少了它的症状是：编译完美通过 → 运行一句错都不报 → 但窗口就是不出来。
没有异常、没有崩溃、没有任何提示，程序就这么静默地什么都不做。

所以安装命令必须显式带上：

pacman -S mingw-w64-ucrt-x86_64-qt6-base mingw-w64-ucrt-x86_64-qt6-5compat

并且要先跑一次 env_check 确认 GUI: 那一行不是 NONE， 再动手写业务代码。这就是我坚持「先做环境自检，再写 500 行」的原因—— 在错误的地基上盖楼，是最高成本的错误。

二、OpenCV 的三个反直觉

这三个点，考试会考、答辩会问、写错了还不会有编译错误。它们属于「不知道就一定会栽」的类型。

反直觉之一：颜色顺序是 BGR，不是 RGB

这道题里它出现了三次：at<Vec3b> 的取值顺序、putText 的颜色参数、 rectangle 的边框色。任何一处写成 RGB 顺序，颜色就会错得很明显。

顺带一提：叠加文字用的是 Scalar(0, 255, 255)，那是 BGR 顺序下的黄色 （B=0，G=255，R=255 → 红+绿=黄）。这个小细节可以顺手在答辩时说出来，证明你真的懂 BGR。

反直觉之二：at<T> 的参数是 (行, 列)

也就是 (y, x)，不是 (x, y)。

写反了会怎样？

不会有任何报错，也不会崩溃——你只是读到了另一个像素。 在方方正正的图上，两种顺序都能"取到"一个值，所以程序看起来完全正常， 只有对着画面逐点核对时才会发现坐标和颜色都对不上。
这是 OpenCV 里最典型的"静默错误"。

正确的写法：

// at<类型>(行, 列) —— 行是 y，列是 x
const cv::Vec3b bgr = image.at<cv::Vec3b>(y, x);

反直觉之三：waitKey 不只是"等按键"

新手容易以为 waitKey 就是个输入函数。其实它还负责两件必不可少的事：

  1. 驱动窗口刷新——不调用它，imshow 显示的内容永远不会真正画到屏幕上。
  2. 处理事件——鼠标点击回调、窗口关闭、键盘输入，全靠它在背后分发。

所以视频模式里必须每帧都调一次 waitKey(delay)， 而且这个 delay 还兼职做了"播放速度控制"：

const int delayMs = static_cast<int>(1000.0 / fps + 0.5);

const int key = cv::waitKey(delayMs);   // 返回 -1 表示这段时间内没按键
if (key == 27) {                     // 27 = Esc
    userInterrupted = true;
    break;
}

为什么 delay 要夹在 [1, 100] 之间？

下限 1：即使源帧率很高，也至少给窗口一次刷新机会， 同时避免 waitKey(0) 那种"无限等待"的语义混进来。
上限 100：万一元数据异常算出几千毫秒，程序看起来就像卡死了。

三、老师为什么要你自己写一个类

题目里 VideoReader 这个类单独占了 15 分。这看着挺小题大做—— 不就是包一个 VideoCapture 吗？

关键在于评分点写的是「按职责划分」和「主程序不直接操作类内部的 VideoCapture」。 所以老师看的不是"能不能读视频"，而是你有没有封装意识。

我是怎么让这条要求「强制执行」的

光靠自己记得别在主程序里写 cv::VideoCapture，是不够可靠的。所以这里用了一个小技巧：

把 VideoCapture 挡在头文件之外

在 video_reader.h 里，cv::VideoCapture 只做前置声明：

namespace cv { class VideoCapture; }   // 只声明，不定义

真正的 #include <opencv2/videoio.hpp> 只出现在 video_reader.cpp 内部， 私有成员用 std::unique_ptr<cv::VideoCapture> 持有。

这样 video_mode.cpp（主程序）根本拿不到这个类型。 谁要是写一句 cv::VideoCapture cap;，编译直接失败（不完整类型）。

这就是所谓的「让编译器当守门员」。比在 README 里写一句「请注意不要这样做」要可靠一万倍。

验证方法（一条命令）：

rg "VideoCapture" src/ include/
# 只会命中两个文件：
#   include/video_reader.h    （前置声明）
#   src/video_reader.cpp      （真实使用）

帧号从 1 开始，还是从 0 开始？

这是个必须"想清楚"而不是"随手定"的细节，因为它会直接影响收尾时的统计。

方案含义风险
1 基（本工程采用） frameNumber() = 已成功读取的帧数 无。屏幕显示 Frame 1 / 750，无需 +1 换算
0 基 与 CAP_PROP_POS_FRAMES 语义对齐 内部是 0、界面要显示 1，两套编号容易混

更关键的是失败时要不要推进帧号：

bool VideoReader::readNext(cv::Mat& frame)
{
    cv::Mat temp;
    if (!m_capture->read(temp) || temp.empty()) {
        return false;          // 帧号保持不变
    }
    frame = temp;
    ++m_frameNumber;              // 成功之后才加
    return true;
}

如果读到末尾（EOF）也把帧号 +1，最后的帧号就会比总帧数多 1， 收尾打印「共处理 N 帧」就多算了一帧。这是一个非常常见的 off-by-one 错误。

四、那 20 分的一致性，其实只靠一行代码

「保存结果」这一块里有一条要求，很多人会理解错：

输出视频中显示的帧号、分辨率和处理 FPS，必须与处理画面一致。

直觉做法是"画两遍"：显示前画一次，写盘前再画一次。但只要你两处的颜色、字号、 文字格式有任何一点不同，就不一致了——而且这种差异肉眼很难发现，扣分却照扣。

正确做法是只画一次：

if (!reader.readNext(frame)) break;   // 自然结束
fpsMeter.tick();

drawOverlay(frame, info);             // ★ 原地画，唯一的一次

sink.write(frame);                    // 写盘
cv::imshow(kWindowName, frame);       // 显示  ← 同一块内存

这就是整件事最漂亮的地方：不需要额外去"保证"一致性，因为两者物理上是同一块内存。

顺序也很重要

必须是「先画 → 再写 → 最后显示」。 如果写成「先写 → 再画」，视频里就没有叠加信息了； 如果写成「先显示 → 再画 → 再写」，屏幕上看到的和视频里的又会对不上。

五、两个 FPS：最容易答错的问题

程序里其实有两个帧率，含义完全不同。混淆它们是这类作业里最常见的扣分点。

名称是什么用在哪能否替换
屏显 FPS 程序实际处理一帧的速度（实测吞吐） 画在画面左上角 —
容器帧率 输入视频本身的 CAP_PROP_FPS 传给 VideoWriter 绝对不行

如果把实测吞吐当成容器帧率传进去，会发生什么？

一段 6 秒的视频，实测处理速度 12 fps。
拿 12 当容器帧率写出去 → 播放器认为这 180 帧只该播 15 秒， 于是输出视频变成了慢动作。

实测数据也印证了这点：本机处理 1280×720 的视频，屏显 FPS 只有 11.8 （因为 H.264 软件编码很吃 CPU），但输出视频的容器帧率仍然是 30， 用 ffprobe 查出来 duration=6.000000、nb_frames=180，完全正确。

FPS 数字怎么算才好看

三种做法的对比：

做法效果
总帧数 ÷ 总时间前期严重偏低，后期几乎不动，看不出卡顿
1 ÷ 单帧耗时数字乱跳，在 18 和 60 之间闪，观感很差
滑动窗口 + 指数平滑（本工程）稳定、对卡顿敏感、首帧不会闪 0.0

核心是两句话：

// 最近 30 帧的平均；次数不足 2 次就返回 0，界面会渲染成 "--"
if (m_stamps.size() < 2) return;

const double instantFps = (m_stamps.size() - 1) / span;
m_lastFps = (m_lastFps <= 0.0) ? instantFps : (0.8 * m_lastFps + 0.2 * instantFps);

为什么首帧要显示 -- 而不是 0.0？

第一帧的时候还没有"时间差"可以算，显示 0.0 会让人以为程序卡住了。 显示 -- 则一眼就知道"还没开始统计"，这是体验细节。

六、报错速查表

现象真正的原因怎么修
程序跑起来没窗口，也不报错 没装 Qt6 运行库 pacman -S mingw-w64-ucrt-x86_64-qt6-base mingw-w64-ucrt-x86_64-qt6-5compat
no Qt platform plugin could be initialized 找不到 platforms/qwindows.dll（插件是运行时加载的） 在 UCRT64 终端里运行；或设 QT_QPA_PLATFORM_PLUGIN_PATH；或跑打包脚本
找不到 libopencv_core-500.dll PATH 里没有 C:/msys64/ucrt64/bin 在 UCRT64 终端里运行
按 Esc 没反应 Qt 窗口需要先获得焦点才能收键盘事件 先用鼠标点一下画面，再按 Esc
输出的 mp4 是 0 字节 release() 没执行，mp4 的索引没写入 本工程用析构函数强制 release，正常不会发生
find_package(OpenCV 4 ...) 报版本不兼容 OpenCV 的 config 用 SameMajorVersion 策略，5.0 与"请求 4"不兼容 去掉版本号：find_package(OpenCV REQUIRED ...)
控制台中文乱码 GBK 代码页 + UTF-8 字节 程序已在第一行调 SetConsoleOutputCP(CP_UTF8)；老终端可 chcp 65001
图片路径含中文读不出来 OpenCV 内部用窄字符 fopen 已加 imdecode 兜底；仍建议用纯英文路径

七、答辩预演：老师可能问的 8 个问题

1. 为什么帧号从 1 开始？

因为我把 frameNumber() 定义为「已成功读取的帧数」， 所以读完第一帧它就是 1，屏显 Frame 1 / 750 不需要额外换算。 而且读取失败时我不推进帧号，所以收尾统计「共处理 N 帧」是准确的， 不会比总帧数多 1。

2. 怎么保证输出视频里的信息和屏幕一致？

因为我只画一次。drawOverlay 原地修改 frame， 然后同一块 cv::Mat 分别交给 write() 和 imshow()。 两者消费的是同一份像素，结构上就不可能不一致——不需要靠两处代码写得一样来碰运气。

3. 主程序真的没碰 VideoCapture 吗？怎么证明？

不但没碰，而且碰不到。video_reader.h 里 cv::VideoCapture 只有前置声明，完整定义只在 video_reader.cpp 里。 主程序包含的头文件拿不到这个类型，写了就编译不过。

另外可以用 rg "VideoCapture" src/ include/ 验证，只会命中两个文件。

4. 屏显的 FPS 为什么只有 12，不应该 30 吗？

这两个是不同的东西。屏显的是实际处理吞吐，包含了 H.264 软件编码的开销， 所以是 12 左右，这是真实测量值，我不去美化它。 而容器帧率取的是源视频的 30，所以输出视频时长仍然是准确的 6 秒。 如果我拿 12 当容器帧率，输出就会变成慢动作。

5. at<Vec3b> 的两个参数是什么顺序？

是（行, 列），也就是 (y, x)。 写反了不会报错，只会读到另一个像素——所以必须记住。 另外 Vec3b 的下标顺序是 B、G、R，不是 R、G、B。

6. 为什么至少要拆两个函数？你拆了几个？

拆了 7 个。原则是：主流程函数只负责编排和错误分支； 凡是可能单独失败（比如读图、创建输出视频）或者被多处共用（比如叠加信息） 的逻辑，都下沉成独立函数。

所以 loadImageStrict、openWithFallback、 drawOverlay 是"必须"独立，而不是为了凑数把 5 行代码包一层。

7. 如果视频编码器不可用怎么办？

我做了 5 级降级：avc1/mp4 → mp4v/mp4 → XVID/avi → MJPG/avi → FFV1/avi， 逐个尝试，全部失败才报错，并且会把试过哪些组合打印出来， 而不是只说一句"失败了"。另外 FFV1 支持任意尺寸， 所以遇到奇数宽高（如 641×481）也能兜住。

8. 为什么不直接 imshow 完就 waitKey(0)？

图片模式确实是 waitKey(0)，因为只需要等一次按键。 但视频模式必须每帧都调 waitKey(delay)——它不只是"等按键"， 还负责驱动窗口刷新和分发鼠标/键盘事件。不调用它，画面根本不会重绘。 而 delay 顺便充当了播放速度控制。
